多模型共识 Mesh 模板设计

01

设计结论

最小且兼容的方案不是新增调度引擎，而是在现有 Mesh Graph 之上增加一个命令模板。

推荐：/consensus = Command + ModelRegistry + ask_user_question + Graph Template

复用现有 graph、显式 task model、Worktree、依赖证据、重试、恢复与最终集成能力。现有 debate 保持顺序链语义，不承担多模型共识协议。

命令层

注册 /consensus，读取任务文本和模型目录，并向 Host Agent 注入受约束的模板指令。

02

端到端架构

/model 是 UI；扩展不调用它，而是读取相同的 ctx.modelRegistry.getAvailable() 目录。

虚线表示命令在生成问卷前读取模型目录；实线表示用户确认后的执行流。

03

问卷与模型选择

ask_user_question 每题最多四个选项，因此展示“模型组合预设”，而不是把全部模型逐项塞入问卷。自定义行仍可输入精确的 provider/model 列表。

问题 1 · 模型数量

  • 3 个模型（推荐，有明确多数）
  • 5 个模型（更稳定，成本更高）
  • 4 个模型（可能平票，由 Finalizer 裁决）

问题 2 · 模型组合

  • 跨厂商组合（推荐）
  • 编码优先
  • 成本平衡
  • 当前 Provider

每个选项使用 preview 展示准确模型 ID。

问题 3 · Finalizer

  • 最强参与模型
  • 当前 Host 模型
  • 独立第四模型
  • 自定义 provider/model
const models = ctx.modelRegistry.getAvailable();

04

两轮共识 DAG

以三个参与模型为例，共 18 个节点。Ledger 节点压缩争议，避免每一轮把全部历史输出重复注入所有模型。

每个实现和修订节点使用对应参与模型；Ledger 可使用较快模型；Finalizer 可使用当前 Host、最强参与者或独立模型。

06

命令模板

命令不直接调用第三方 Tool；它向当前 Host Agent 发送严格模板，由 Host 正常调用 ask_user_question 和 mesh。

pi.registerCommand("consensus", {
  description: "Run a task through multi-model implementation and consensus",
  handler: async (args, ctx) => {
    const models = ctx.modelRegistry.getAvailable();
    const catalog = compactModelCatalog(models, ctx.model);

    pi.sendUserMessage(buildConsensusPrompt({
      task: args,
      catalog,
      fixedPolicy: {
        worktree: true,
        rounds: 2,
        decision: "majority"
      }
    }));
  }
});
07

实施计划

建议分四个小提交完成；每一步均可独立测试和回退。

Step 1
命令与模型目录

注册 /consensus；从 ModelRegistry 获取可用模型；生成紧凑、去重、跨 Provider 的候选目录。

Step 2
Ask User Question 模板

一次询问模型数量、组合和 Finalizer；支持预设 preview 与自定义 provider/model 输入。

Step 3
DAG 生成器

用纯函数展开 18 节点 Graph，保留每个参与者的显式 model，并强制 Worktree 与 Finalizer integration。

Step 4
测试、文档和发布

覆盖模型校验、DAG 拓扑、问卷 Prompt、Worktree 交接、投票汇总与打包加载。

处理

10

验收标准

交互

  • /consensus 无任务时给出提示
  • 一次 ask_user_question 完成选择
  • 自定义模型 ID 能被严格校验

执行

  • 参与模型相互隔离
  • 两轮辩论与修订依赖正确
  • Finalizer 获得 Commit、Patch、Ledger 和投票

结果

  • 只生成一份 Canonical Result
  • 多数票和少数意见可审计
  • 最终实现包含验证结果与 Handoff
