核心结论

不建议重写 pi-mesh，也不建议只把 resume 改名为 SendMessage。目前最需要修的是：共享并发下排队能否完成、暂停后的调度器能否恢复、会话是否真能续跑、工作树是否成功交付、取消后旧任务是否彻底收尾。最新 Claude 值得借鉴的是这些边界的仲裁，以及能指导模型采取下一步的结果协议。

问题明细：先修可导致卡死、失真或越界的路径

P1：优先修复的正确性/信任边界问题。P2：随后处理的协议与运维可靠性问题。除明确写“已复现”外，均为代码与可达触发序列的静态确认，不冒充故障实测。

F1 · P1 · Host project trust 在 Child SDK 重建时丢失

触发：Host 未信任项目，但仍允许运行 bundled/user Agent。上层只用 trust 筛 Agent 和 mesh settings；构造 Child 时没有传入该 trust。

根因：SettingsManager.create(cwd, getAgentDir()) 默认 projectTrusted=true。项目 shellCommandPrefix / shellPath 等可再次生效；DefaultResourceLoader 先 resolve packages，之后才按 noExtensions 过滤，所以“禁用扩展发现”不能等价为“完全不解析项目包”。

影响边界：这是丢失已有信任决策，不是要求把 in-process 变成 OS sandbox。包安装副作用有可达代码路径，但本轮没有执行不可信安装或危险 shell 前缀。

最小改进：Host → Manager → Runtime → SettingsManager 显式传递 trust，缺省 fail-closed；只解析被批准的资源，不为读取子代理资源走完整默认包发现。

F2 · P1 · Direct 队列：前台提前返回，共享槽位释放后可能不唤醒

QA 1 / 2 已复现前台实际 11 ms 返回 queued；外部槽位释放 600 ms 后仍 available=1、waiters=0、Direct=queued、mockCalls=0。真正 limiter waiter 的对照能正常唤醒；额外启动另一 Direct 并完成才推进滞留任务。

两个独立表现：① 满额时 spawn 只把 record 放入本地 queue，没有 promise，前台 await record.promise 实际 await undefined，直接返回 queued / No output。② 槽位被 Mesh 占满、Direct 自身没有 running 任务时，Direct 没注册 Fleet waiter；外部释放槽位也没有事件来调用本地 startNext。

最小改进：record 从 queued 创建时就持有稳定 completion promise；所有启动等待都通过可取消的 FleetLimiter.acquire，避免“本地 queue + available 快照”成为另一套唤醒机制。

F6 · P1 · 工作树交付失败仍 succeeded，下游可能读到错误基线

F9 · P1 · shutdown/finalizer 应按实际存活资源，不只看业务状态
  • Direct 默认非 persistent Agent 完成后保留 execution；不可 resume 也常驻到 Host shutdown。1024 只限制写盘，不清内存 records。
  • Child close 只有 abort/dispose，没有发送扩展 session_shutdown；已批准扩展若靠该事件清 timer/socket，生命周期不闭合。
  • Mesh 先 pause 再 shutdown 时，仍在排空的 child 因 run=paused 被跳过；lease 却会释放。

checkpoint 竞争（P1，静态候选）：同 session 两个 Manager 先各恢复 paused 快照；A 取得 lease 并 resume，B 的 grow/touch 没有 ownership/revision 检查，可把旧快照写回。原子 rename 不能防 lost update。应让每次 checkpoint mutation 都经过 ownership 校验，重新取得 lease 后核对磁盘 revision。

05

怎样让 AI 真正会排错，而不是反复重试

上一轮补充的“列出冲突参数 + 告知保留字段 + 新建/steer 两条路径”是对的，但只解决了入口冲突。错误协议还应说明当前状态、是否可重试、需要先发生什么、下一次到底调用哪个工具。

失败类别给模型的正确行动不要这样引导
参数冲突列出本次具体冲突字段，给合法 continuation 形状；只有确实要改变启动配置才新建。笼统说 invalid options；或让模型只传 resume 而违反 required schema。
running / queued补充任务用 steer / 未来统一 send；需要结果用 wait。queued 状态若尚不支持 steer，应说明未投递。建议不断 resume 或重复 spawn 同任务。
stopping / settling明确旧 execution 尚未退出；等待原 completion，保留一条待处理消息。把 stopped 当成资源已经释放。
用户取消停止自动恢复，说明需要新的用户授权才能继续。提供自动“换一个 ID 重做”的绕行建议。
并发已满排队或等待已有工作完成，返回 wait 状态与目标；不制造轮询风暴。把所有 quota 错误都标 retryable=true 而不给条件。
会话/journal 缺失明确无法原样恢复；列出现存 transcript/artifact，必要时提出显式的新执行修复路径。静默创建新会话，再声称是原 session 的 continuation。
handoff 失败返回保存路径、交付是否有效、哪个步骤失败；阻断后继 writer。正文报 error，外层仍 succeeded 并继续下游。
回合/时间上限partial=true、stopReason、已保存的结果、可继续的 ID；区分 transport 失败与任务不完整。把“有一段文本”视为完整完成，或统一描述为用户取消。

短期：保留旧 API，修行为与说明

用现有错误文本先承载稳定 code、currentState 与 nextAction 即可，不必引入错误类层级。若另放 details，注意 Pi 的 LLM 主要读 content，不能只给 UI 写机器字段。

# 建议的错误形状；不是当前已实现字段
AGENT_STILL_STOPPING
agentId: …
state: stopping
retry: after_previous_execution_settles
next: wait for the existing agent; do not spawn a duplicate

抛错仍遵循 Pi execute 错误通道；普通“查询到 child failed”可以是成功的状态查询，但必须把失败与正文来源清楚展示。

中期：可选统一发送入口

# 设计建议，不是当前工具名
send_subagent(agent_id, message)
  running → queue direction
  settling → serialize behind the old run
  terminal + resumable → resume same identity
  user_cancelled → refuse
  missing evidence → refuse + artifacts

先只支持当前会话 Agent ID；不同时引入跨会话寻址、团队名称复用、远端 peer、递归调度。以后有真实需求，再复用已有独立会话通信能力。

不改变现有 mesh.message_send 的纯 mailbox 语义，否则简单写消息突然启动模型，成本与取消约定都会变得隐蔽。

06

推荐改进顺序与验收门槛

批次范围最小验收
A · 先修不变量trust 传递；Direct queued completion；pause/resume/cancel 收敛；handoff 成功提交时机。不可信项目配置不生效；所有前台等待覆盖排队；暂停排空竞态不丢循环；无 loop 的取消可收敛；交付失败不启动下游。
B · 恢复是真的恢复专属 Child session 根；ready 即保存 sessionFile；同 ID continuation 串行；worktree 自身 attempt 基线接续；shutdown 清理。首次真实 in-process 执行中断后可辨识恢复；旧 generation 不能覆盖；下一 attempt 看到上一份已保全文件；关闭后无执行/清理悬空。
C · 排错与可观测性稳定错误 code/nextAction；partial/stopReason；通知与记账代际；schedule 重启；过期 proposal 可 deny。按错误提示生成的下一次调用能通过真实 schema；查询不增加模型用量；每次完成只通知一次；重启不必新增 schedule 才恢复。
D · 选做增强统一 send_subagent；稳定 prompt 前缀；上下文快照预算；输出边界标记；多 Manager ownership 检查。先建立状态与来源模型；cache 不能绕过最新权限；任何别名/新工具不破坏旧 resume 与 mailbox 兼容。

现在不做

不照搬 Claude 的 JS Workflow VM、world runtime、remote sandbox、implicit team、默认三级递归、observer 或自动 push/PR。当前最重要的收益来自修补已有实现，而不是扩大工具数量或“功能对齐率”。
