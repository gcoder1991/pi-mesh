最重要的区别
可通信 ≠ 自动协作

先给直接答案

  • 同一 Mesh run 内：可以。8 种 operator 都给节点同一套 mesh_control 邮箱；但消息需要收件节点主动 inbox，不能直接唤醒或复活节点。
  • Direct Agent 之间：默认没有直接通道。前台、后台都一样，通常由 Host 读取结果后 steer/续跑转达；后台不等于独立 Pi peer。
  • 独立 Pi 会话之间：可以实时协调。加载 cross-session、同机同 agentDir 命名空间、endpoint 存活且接收方 accept；busy 排队，idle 可触发新 turn。
  • debate / reflection 不等于实时群聊。当前都是有界串行链；supervisor / mixture 的最后一个节点是事后汇总者，不是一直在线的主管。
  • 推荐组合：Mesh 管受控任务，cross-session 管独立 Host 横向协调；先通过 Host 转达，不把每个 managed child 默认暴露到全局 peer 网络。

02

三条通信路径，不是一个“Agent 聊天总线”

纵向 · Host ↔ Direct

父代理控制与结果回传

Host 用 Agent 创建、get_subagent_result 查询、steer_subagent 改变正在运行任务的方向；终态 continuation 仍用当前 resume 入口。

Direct child 默认只拿自己的工具，不自动获得其他 Direct ID 的消息工具，也没有 Mesh mailbox。中途 activity/UI 更新不等于发给父模型的一条业务消息。

前台/后台只改变 Host 等待方式，不创建 peer 网络。

M：compat-extension.ts:81–153；session-agents.ts:85–105,149–172；subagent-runtime.ts:151–164。
run 内 · Mesh 节点 ↔ 节点

持久、显式读取的邮箱

mesh_control send / broadcast / reply / inbox / ack。每次调用校验 run、node、attempt 是否活跃；目标为同 run 的节点 ID 或 host。

写入项目 .pi/mesh/messages/<runId>，按收件人限制未读字节。默认单消息 32 KiB、单收件人未读总量 1 MiB。

Queued 表示已入邮箱，不表示读过、执行过或完成。没有自动注入到 child prompt 的消费循环。

M：control-extension.ts:25–97；store.ts:141–209；manager.ts:681–693。
横向 · 独立 Pi ↔ Pi

在线实例的 IPC 消息

cross-session 用私有注册文件发现 live runtime，再以 Unix socket / named pipe 发送 plain text。模型使用 list_pi 和 send_pi_message。

接收方始终以 steer + triggerTurn 提交给 Pi：忙时排队，闲时可以开始新 turn。离线实例无法收件，扩展没有持久消息队列。

submitted 只确认扩展 API 提交，不是 durable delivered / processed。

C：303–381,531–576,628–670,694–732。

依赖边不是通信权限

dependsOn 决定什么时候运行，以及自动附带哪些前驱结果；它不限制同 run 的收件人。没有依赖边的两个 running 节点也可以发消息。allowedSubagents 限制可提出的 growth 类型，不是“允许联系哪些节点”的 ACL。

03

Mesh 8 种 operator：具体能怎样交互？

以下均以真实生成的 DAG 为准。需要实时往返时，还必须有两个节点同时运行、并发额度足够，且双方主动检查 inbox。没有任何 operator 自动开启聊天循环。

模式当前实际拓扑节点之间能否交互容易误解的地方
graph按 tasks 的 dependsOn 调度。同 run 任意节点可被投递；同时运行节点可通过 inbox/reply 往返；依赖节点另有自动结果传递。没有边不等于不能发消息；有边不等于发送后立即唤醒。
parallel不自动加边；显式 dependsOn 仍保留。适合并行同事交换发现，但要自行读取消息；没有边时不会自动获得兄弟节点输出。并发上限=1 时仍轮流执行，不可能同步往返。名字不强制删除依赖。
sequenceA → B → C，有界串行链。A 的结果自动交给 B；A 可提前给 B 留邮件。B 可以回复 A 的邮箱，但已完成的 A 不会自动重启读信。是交接链，不是两个在线 Agent 互相等回复。
race保留显式依赖；首个 succeeded 触发取消剩余任务。胜出前若节点并行，仍能互发邮箱消息。胜出后未读消息不保证被处理。若目的是独立候选竞争，建议减少互相影响。
supervisor最后一个任务依赖所有前面的 worker。worker 可并发交换消息；最后汇总者启动后自动获得各 worker 结果，也可读此前投给它的邮箱。最后节点不是从开头就在线的主管，不会实时指挥尚在工作的 worker。
mixture与 supervisor 相同的最后节点 fan-in。专家间可自行通信；综合者在专家完成后处理成果。不是额外的路由网络或持续专家会话；与 supervisor 的差异主要由任务/prompt 赋予。
reflection与 sequence 相同的有限串行链。生成 → 评审 → 修订可以通过任务链与前驱输出实现。不会自动复活原生成者，也没有内建直到收敛的循环。
debate与 sequence 相同的有限串行链。立论 → 反驳 → 回应可展开成多个节点，每步读取前驱证据。不是实时多方聊天室。要 N 轮就明确建 N 轮任务，或另设计受预算约束的常驻协作。
实现：M manager.ts:367–374,465–490,681–693。本轮隔离测试执行了全部 8 种 operator 的实际 create/拓扑编译；另验证 parallel 不删除显式 dependsOn。

YAML workflow 与 growth

  • stages 编译为同一个 run 的带前缀节点，例如 review.critic；仍使用同一邮箱。stage 不是新的权限或会话边界。
  • stage 依赖变成入口/出口之间的 DAG 边。不同阶段节点即使不同时运行，也可预留消息，后续节点必须主动 inbox。stage 级 race 当前不支持。
  • growth 是 Host 批准后增加节点，不是 child 自己启动一个自由递归调度器。新增节点仍受 run/attempt 边界与并发限制。
M workflows.ts:86–128；manager.ts:320–336；control-extension.ts:58–71。
04

状态比 operator 更能决定“这封消息会不会被处理”

Mesh 的状态矩阵

状态Child control投递与读取Host 可做什么
run running，node running，attempt 匹配status/send/reply/inbox/ack 可用。读取自己的未 ack 邮箱；重复 inbox 不会自动 ack。可投递邮箱，也可 steer 现有 execution。
目标 node queued目标自己不能调用 control。其他活跃节点可给它留消息；不会因此启动。变成 running 后可以读取。可预留邮件；不能把 queued node 当 running 来 steer。
目标 node succeeded / failed / cancelled目标自己不能调用 control。只要发送方仍活跃，投递仍可写入；不会自动复活目标。可读 mailbox / artifacts；继续工作需要合法的调度/重试操作。
run paused，child 仍在排空所有 child control 都拒绝，包括只读 status/inbox。Host 邮箱操作仍可写读；child 要等恢复后的有效运行窗口。若 node 仍 running 且 execution 存在，Host steer 仍可能可用；这和 child control 的 gate 不同。
旧 attempt 句柄拒绝调用。邮箱按 nodeId，而非接收方 attempt 分区；新 attempt 可以读旧未 ack 消息。应识别消息是否仍适用，不能把旧代际内容无条件当新指令。
run 已结束/取消全部拒绝。文件可能保留，但不会因为新邮件自动恢复。保留还受 run retention 清理影响。查询与归档不等于重新执行。

cross-session 的状态矩阵

在线实例状态是否可收实际行为重要边界
busy + accept可以，在限流/提交上限内。Pi steering 队列在 agent loop 的安全检查点处理；不主动 abort 当前工具。不是保证任意两个工具调用之间立即处理；注册 status 也可能滞后。
idle + accept可以。仍传 steer + triggerTurn，由 SDK 启动新的 prompt/turn。不是 fork 新 Agent，也不是从磁盘恢复已退出实例。
刚 abort，但 runtime 未退出仍可能可以。取消任务不等于注销 endpoint；之后的 peer 消息仍可能触发 turn。该项目没有 Claude managed-Agent 那样的用户 stop 防复活仲裁。
inbound=refuse拒绝入站。仍可被发现，也可主动发送。非法 flag 值也走 refuse；收件策略不是完整的出站权限控制。
shutdown / 已退出不可以。正常 shutdown 删除注册和 socket；异常退出后由发现过程尽量回收。没有离线队列；强杀后残留只有 PID 可证明死亡才回收。
同 session 重启、reload 或标准 switch新 runtime 可以。生成新 instanceId、token、ref；旧 incarnation 不再有效。不能把持久 sessionId、名称和某次存活实例混为一谈。

共同原则：先确认发送动作的收据含义，再决定是否等待结果。Mesh 的 ack 是消费标记，不是任务完成；cross-session 的 submitted 甚至不保证已进入模型历史。

前台、后台、隔离、RPC：哪些会改变通信？

模式/开关实际影响不能据此推断
Direct foreground / background主要决定 Host 等待 completion 还是先拿 ID；默认均无 peer-to-peer 工具。background 不等于独立 OS 进程、独立终端或 cross-session peer。
scheduled Agent到期调用同一个 Direct Manager 启动任务，通信边界不变。定时执行不等于常驻在线接收者；且上一轮已发现 scheduler 重启初始化缺口。
inherit_context复制父上下文片段进入本次 prompt。不是共享内存、实时订阅，也不是通信通道。
isolated=true清空该 child 的附加 extensions/skills。不删除 Mesh 强制提供的 mesh_control；逻辑隔离不等于 OS 沙箱。
worktree隔离代码工作目录；Mesh control 仍指向原 run root 的共享邮箱。Git worktree 不隔离 IPC/邮箱，也不自动共享其他节点未交付的代码。
persist_session / --no-session影响会话落盘和后续恢复。in-memory session 也能有 live endpoint；持久化会话文件不代表离线时能接收 IPC。
独立 TUI / RPC成功加载并绑定 cross-session 后均具备注册能力；TUI 额外有 @ 自动补全。通信能力不只属于 TUI；RPC smoke 能加载不代表已验证互通。
print / JSON 一次性执行标准路径会绑定扩展；仅在进程/Session 存活且 endpoint ready 时具备收发条件。server.unref 不保活进程；不能把短任务当长期在线服务。
in-process managed child默认 noExtensions；只有资源 allowlist、Agent extensions 配置及 API 兼容等条件满足才可能加载 cross-session。显式工具列表还须允许出站工具。不是默认支持的集成桥。同 PID 不妨碍新 instanceId；PI_MESH_CHILD 也不会自动阻止 cross-session 注册。
同机不同 cwd / 不同 agentDir相同 agentDir 命名空间下，不同项目 cwd 的 peers 可互相发现；不同 agentDir 默认互不可见。cwd 不是 peer 通信的安全隔离边界；同机不意味着必然在同一命名空间。
M subagent-runtime.ts:95–102,138–164,187–212,297–299、pi-process.ts:78–115、rpc-child.ts:49–52；C 24–27,384–395,744–843。两项目 SDK 版本不同，显式 Child 集成不能只凭静态“可以加载”就宣称验证通过。

现在就能采用的协作方式

A. 同一 Mesh run：显式邮件协议

以下是节点内的工具参数示例；收件人应使用 status 展示的 nodeId，不是 Agent 类型名。示例中的 reviewer 必须实际存在于该 run。

// mesh_control：先看拓扑，再发送
{ "action": "status" }
{ "action": "send", "to": "reviewer",
  "content": "检查已保全的补丁；请返回具体失败项。" }

// 接收节点主动读取、回复，再确认已消费
{ "action": "inbox" }
{ "action": "reply", "messageId": "<原消息ID>",
  "content": "发现边界条件缺口，证据在……" }
{ "action": "ack", "messageId": "<原消息ID>" }

在 task 中明确：在哪些工作检查点读 inbox、是否必须回复、何时停止等待。不要靠高频轮询制造“实时感”；依赖方未运行时也不要等待它实时回答。

child 的 broadcast 默认发送给其他节点，不含 host；要通知 Host，显式 send to=host。Host 仍需主动查看对应 inbox。

B. 独立项目：Host 横向协调

目标未指定时先 list_pi；按责任、准确名字和 cwd 选人，不优先挑 idle。用户已给 @name [ref] 时直接用该明确目标。

// send_pi_message 的参数示例，不执行发送
{ "target": "@backend [<实际ref>]",
  "message": "已确认订单接口改为 /v2/orders；请据此检查调用点。",
  "summary": "订单接口路径已确认" }

只发送对方确实需要的发现、决策、问题或状态；不发送例行进度，不把本会话能完成的工作随手转移出去。

若需要对方实际确认完成，要求一条明确业务回复并保留关联标识；submitted 不是“对方已处理”。超时后先确认现状，不盲目重发造成重复执行。

C. 两个 Mesh run / 两个项目：先通过 Host 转达

  1. 本地节点用 mesh_control send to=host 留下发现。
  2. 本地 Host 用 mesh message_inbox，指定该 run 与 nodeId=host 查看。
  3. Host 确认相关性与来源后，通过 cross-session 联系远端Host。
  4. 远端 Host 根据自己的 run/node 状态，用 mesh steer 或持久 mailbox 转达；若是 Direct，则用 steer_subagent 或合法 continuation。
  5. 回复按相反方向返回，不把对方消息解释成用户批准、权限变更或 topology approval。

这条 Host 转达路径可以组合现有工具完成，但不是已经实现的自动桥接。当前 Mesh 没有“新邮箱事件自动转发到 cross-session”，cross-session 也不知道 Mesh run/node/attempt。只有证明人工/模型转达确实不足，才补一个很薄的 Host 适配层。

07

应从 pi-cross-session 借鉴什么？

思想值得保留的实现在 Mesh 中的最小落点
身份分层持久 sessionId + 每次启动 instanceId + 可读 name/ref；协议核验双方身份，歧义拒绝。UI 显示可读名，但控制按 runId/nodeId/attempt 或 Direct ID/generation 绑定，不用 PID/名字替代执行身份。
发现与传输分离私有注册文件用于发现，主动 hello 探测 endpoint；单次 IPC 传输，无 daemon、DB 或常驻路由服务。跨进程 Host 继续复用现有 cross-session；同进程 managed child 没必要绕 Unix socket 重新实现内部通信。
忙时排队、闲时唤醒始终 steer + triggerTurn，交给 Pi loop 处理真实运行状态。内部实时通知应由 Host 接入已有 execution；如果涉及恢复必须经过 quota、用户取消、generation 与 session 证据检查。
精确选人责任、准确名称、cwd、显式 @ref；busy/idle 不是路由偏好。对 run 节点显示 agent 类型之外的 node task/责任与执行代际；默认只在当前 scope 寻址。
拒收与有界流量accept/refuse、帧上限、token bucket、短期去重、运行期提交计数上限。保留 Mesh 邮箱字节上限；若加自动通知，使用聚合提醒与总轮数/预算，而不是每封邮件直接启动新模型调用。
诚实的回执明确声明 submitted 不是 durable acknowledgement；超时不自动重试。区分 stored、consumed、业务完成和 artifact 可交付；不用同一个“成功”覆盖这些不同阶段。
保留来源且低干扰展示来源 metadata、折叠摘要、展开正文，并声明不是用户批准。保留原 sender、attempt、关联消息和转达 Host；但真正权限要由 Host/工具策略执行，不能只靠一句免责声明。

实现细节：cross-session 的 MAX_PENDING=50 是成功提交后累加、agent_settled 时整体归零的计数器，不是精确的未消费队列长度。30 秒 heartbeat 也不是基于时间自动失效的租约；live 判定依赖 endpoint 探测。

和最新 Claude 放在一起看

能力pi-meshpi-cross-sessionClaude 2.1.266
创建 / 联系已有对象Agent spawn/resume + steer；Mesh mailbox 与 steer 分开。只联系现有 live runtime，不创建或恢复离线对象。Agent 纯 spawn；SendMessage 可投 live，也可恢复 stopped managed Agent。

暂停/取消意图已有 fencing，但 pause/cancel/resume 与 drain 衔接有已复现缺陷。普通 abort 不拒收；idle 消息可能再次触发 turn。managed Agent 有 stoppedByUser、userStopCount 与恢复锁；不允许模型绕过用户停止。

重要区别：cross-session 的 idle 是“进程还活着但当前没有 turn”；Claude 的 stopped managed Agent 可能需要重新构造执行。两者不是同一种恢复。借鉴统一体验前，必须先确定消息是否允许启动计算。

最新 Claude 的价值不在 SendMessage 这个名字，而在恢复互斥、用户取消来源、身份稳定与结果解释。相同不变量也可以在 resume/steer 分离的 API 下实现。

需要改进的地方：先守住边界，再增加自动交互

P1 为优先正确性/安全边界；P2 为协议与使用体验。下面将当前实现事实、既有复现和新增静态风险分开，不把建议写成已实现功能。

R1 · P2 · 把模式名字、通信工具和实际消费方式说明白

当前工具提示强调 topology/growth，却不足以让模型知道 mailbox 需要主动 inbox，debate/reflection 是链，supervisor 是事后汇总。最小收益来自补文案与示例，不是增加新 operator。

建议：明确 send=stored、不自动唤醒、inbox/ack 的时机；把 sender/recipient 的活跃条件放进工具描述和错误提示。对“等待一个尚未运行的依赖节点回复”给出可执行排错路径。

M control-extension.ts:19–35,45–57,96–97、pi-process.ts:78–81、manager.ts:367–374。
R2 · P1 · 先修 pause/cancel/queued，再做实时消息唤醒

上一轮已实证：Direct queued 无稳定 completion/外部唤醒；pause drain 内 resume 丢 loop；已排空 paused run cancel 卡住。通信层如果自动恢复执行，会放大这些问题。

本轮另以真实 control tool 验证：run paused 时连 status/inbox/ack 都被统一拒绝。应将“读取状态/已到消息”与“新增执行/改变方向”的策略分开，而不是简单删除所有状态检查。

建议：先保证调度 loop、execution 和代际清理一致；再定义暂停时允许哪些控制操作。用户取消要记录来源，不能因 peer 消息自动转为 running。

M session-agents.ts:94–165、manager.ts:229–264,425–426,503–514、control-extension.ts:35。既有 QA 1/2/4/5 + 本轮 mailbox contract 检查。
R3 · P1 · 不宜直接给所有 managed child 加载 cross-session

默认状态：不会自动加载。显式放行后：cross-session 没有 PI_MESH_CHILD gate，按每次扩展实例生成 endpoint，可能让 child 获得跨 run/cwd 的全局 peer 可见性。

目前 Child close 只 abort/dispose，没有发扩展 session_shutdown；因此可能留下注册、socket、heartbeat。C 的 heartbeat 还会同步调用已失效 API 的 getSessionName，存在清理后抛错风险。该风险有源码路径，本轮不将它冒充已复现 Host 崩溃。

此外 idle triggerTurn 经 SDK 发起计算，不经过 ManagedSession.prompt 的同一入口；若直接接入 child，必须重新核对 fleet 额度、maxTurns、usage、artifact、onComplete 和取消约束是否仍受 Host 管理。

建议：默认只给 Host 暴露 cross-session；内部实时通知走 Host 管理的 execution。只有生命周期已闭合、权限与 SDK 版本已验证后，才考虑少数显式授权的 child。

R4 · P1 · peer 来源声明不能充当权限隔离

cross-session 的 Unix owner/mode、token、endpoint 身份检查是实际 admission 防线；其明确不抵抗恶意同 UID 进程。cwd、项目名与 ref 也不构成权限域。

custom message 的正文包含“不是用户批准”，但 SDK convertToLlm 将这类消息转为 user role，customType/details 不是独立的模型权限通道。正文不会直接走 slash-command 入口，不代表不会影响模型。

建议：Host 明确 peer-origin 输入不能批准敏感动作、扩大工具集、提交 growth decision 或改收件策略；保留结构化来源与正文边界，最终由权限机制执行，而非只依靠提示词自律。此前 Host trust 传递缺口也应优先修复。

R5 · P2 · 不把 submitted、ack 与任务完成混在一起

cross-session 同步 API 返回后就回 submitted，而底层 sendCustomMessage 的异步错误仅报告 extension error；消息可能尚未持久化或被模型处理。Mesh ack 同样不证明任何业务操作完成。

建议：业务上必须完成的请求增加明确回复/关联 ID；超时先确认，保持“不盲重试”的策略。只有确实需要断线恢复才加持久 outbox，优先复用已有 spool，不把所有状态消息升级成事务队列。

自动往返还要有限的总轮数、TTL 或任务预算；token bucket 与相同文本短期去重不能阻止不断变化的“收到—再确认”对话无限消耗模型调用。

R6 · P2 · 消息身份、重试代际与广播部分成功需要明确

Mesh sender attempt 会校验，但目标邮箱按 nodeId；新 attempt 能看到旧消息。这对续跑可能有用，但不能默认认为每条旧消息仍适用。当前 node→node 没有 run 内按边的通信 ACL，应如实描述。

Mesh broadcast 逐个 putMessage，不是跨收件人事务；后一个邮箱满额时，前面可能已经保存。若模型只看到整体异常后重发，会产生重复消息。该部分是静态风险，不是本轮新增故障实测。

建议：显示 sender attempt 与消息时间，区分“发给稳定节点”还是“当前 execution”；若增加自动消费，先建立去重/重投契约。广播错误应返回逐收件人收据，而不是假装全部失败或全部成功。

R7 · P1/P2 · 交流不能掩盖交付和完成通知的失真

最终建议：分层组合，而不是合并重写

顺序最小改动方向验收标准
1 · 现在就能做保留现有三条路径；补 operator 真正含义、邮箱消费示例、错误状态与收据说明。跨 run 先由 Host 转达。模型知道找 nodeId 还是 @ref；不会把 stored/submitted 当完成；不会等待尚未启动的依赖实时回复。
2 · 优先修底座trust 传递、queued completion/唤醒、pause/resume/cancel drain、扩展 shutdown、持久会话与 worktree 交付。被暂停/取消工作不会因新消息失控重启；无旧 execution/endpoint 悬挂；成果可验证后才 succeeded。
3 · 薄 Host 桥接只有跨会话转达频繁时，复用现有 cross-session 与 Mesh mailbox/steer；显式映射 peer incarnation 到本地任务，保留来源、授权和关联 ID。不跨 scope 误投、不隐式创建任务、不传递权限；超时/重复/终态目标有明确行为。
4 · 按需实时协作有明确需求再增加内部 mailbox 提醒或常驻协作；接入现有 Host execution，不默认给所有 child 加 peer endpoint。受 quota、总轮数、取消来源、generation 与 once-only accounting 约束；不会形成无限互相唤醒。

现在不需要

不需要 Redis、消息中间件、统一大型 AgentBus、跨机器 relay、重写 YAML workflow、默认多轮群聊，或复制 Claude 的整个团队/远程状态机。当前最大的收益是让已有能力语义准确、生命周期闭合。

选型口诀：并行同事用 Mesh mailbox；有序交接用 DAG evidence；跨项目 Host 用 cross-session；长期自主对话另设显式预算与停止协议。
