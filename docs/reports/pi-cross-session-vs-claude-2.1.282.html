对比基线与证据边界

两侧证据强度不同，先声明再对比。表格以已发布版本为基线；本轮补丁（Mesh 0.7.1 / Cross 2.2.1）补齐 Mesh/Direct 输出与错误的防权限转嫁提示，保留旧 Windows 管道格式，并撤回进程全局端点导出。原生 Windows IPC/ACL 仍未实测。

pi 侧（源码级）

本仓与 pi-mesh 仓已发布版本：cross-session 2.2.0（735968f）、pi-mesh 0.7.0（78e1ca1）。行为取自源码与 README；全量测试 82/82、真实 SDK 双插件 8/8 通过（2026-09-25 本机运行）。

02

三个系统概览

Claude 把"同机跨会话"与"多会话团队"拆成两个功能；pi 侧是一个传输层（cross-session）加一个编排层（mesh），经 bridge 打通。

Claude · Cross-session messaging

2.1.224+ 默认启用，零配置。每个交互会话启动即绑定 Unix socket（macOS/Linux，/tmp/cc-socks/<pid>.sock，srw-------）；Windows 2.1.239+ 用命名管道。模型用 ListAgents 发现、SendMessage 按名投递。

可达范围：同机交互/后台会话；Remote Control 连接时可及其他机器与 Web 会话。

uds/named-pipe按名寻址默认开启

Claude · Agent teams（实验）

CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 显式开启；2.1.178 起为隐式团队（TeamCreate/TeamDelete 已移除）。lead 与 teammate 各是完整 Claude Code 会话，tmux/iTerm2 pane 后端拉起；经共享文件任务列表 + mailbox 直接互发，不经 lead 中转。

官方自述已知限制：会话恢复、任务协调、关停行为。

实验开关共享 task listtmux 后端

pi · cross-session + mesh

cross-session：peers 注册文件（随机实例 ID + bearer token）发现，认证 hello 两阶段协议，busy 排队到安全 settled 门控提交。mesh：Host 拥有的 DAG、mailbox（ack 制）、growth 提案、attempt 证据与 worktree 交付。

两者经 bridge 固定路由打通：跨会话消息可精确路由到对端 mesh 节点或 direct agent。

认证握手回执状态机bridge→mesh/direct

06

安全与权限模型

Claude

边界 = 文件系统权限 + token 帧。 socket 目录兽医式校验（symlink/uid/race 分类）；authRequired 下无 token 帧拒连（静态证据）；子代理/对端消息带多变体来源声明与 permission-laundering 指令——已提取的消息防护包含提示规则，局部静态提取未确认对应的 tool_call 门禁；这不证明其他路径没有强制控制。

token 帧 + key 文件防线在提示层

pi cross-session

POSIX 边界 = OS 用户。 注册 token + 路径随机化 + 拒 symlink；peer 文本不构成用户意图：显示层声明 + 机制层 tool_call 门禁（拦 peer/已取消回合的已枚举入口）。同 UID 恶意进程仍可读取 token；Windows 则依赖注册文件 ACL，扩展没有配置或验证该 ACL，不能直接断言与 POSIX 等价。

bearer token 握手机制级门禁（限定面）许可链不越权

逐攻击面裁决（攻击者=消息内注入的指令；只计双方实际存在的机制，非宣传语）：

攻击面pi 2.2.0Claude 2.1.282裁决

伪造来源（消息内文本自称"来自用户/系统"）来源标签由进程内事件决定，消息正文不能修改该字段；语义注入仍需提示/权限防护已提取来源声明；其他来源校验未完全核查不作强弱裁决

任意 Bash / 第三方 / MCP 工具明确非目标，不分类；宿主权限系统兑底同样不包；宿主权限系统兑底平手（同一兑底）

07

已知问题与边界

Claude 侧

· #86385：桌面运行时 send_message 送达队列但不触发回应回合（2.1.227 回归，2.1.231 仍复现；2.1.282 状态未知）。
· 隐私环境变量静默关闭通信；诊断靠 /list-agents 是否存在。
· agent teams 官方自述限制：会话恢复、任务协调、关停；历史上有 malformed mailbox 消息导致每秒报错的 crash loop。
· 突发消息在 2.1.236 前存在"报告已发、接收方丢弃"的窗口。

pi 侧

· 同 UID 恶意进程可读注册 token 冒充发送方——显式文档化边界，非疏漏。
· 256 incarnation 预算耗尽后入站/出站（含 bridge）全部拒绝且不补充；SIGKILL 无法清理，靠 PID 死亡确认回收。
· 队列 30s TTL、50 待投上限：长会话长任务协作需主动 ack。
· cross-session-resume 不重放被丢弃消息（设计决定，非缺陷）。

08

结论与可借鉴清单

两者目标不同：Claude 要"开箱即用 + 跨机器"；pi 侧要"可审计的授权链 + 结构化跨 agent"。不必互相重写，各有可偷的招。

Claude 领先处（可借鉴）

1. 零配置默认启用——信任本机用户即开箱互通。
2. Remote Control 跨机器/Web 会话可达。
3. agent teams 的共享任务列表作为一等领域协调原语（我们只有 mailbox+growth 提案）。
4. 2.1.277 子代理结果视觉标记——一行渲染改动的注入加固。
5. CLAUDE_CODE_MESSAGING_SOCKET 导出到 hooks/Bash，便于外部工具寻址。

pi 已验证能力（不等于 Claude 未做）

1. 认证握手对等（双方都有 token；Claude 亦无静态版本协商证据），能力协商+旧端拒绝回执仍领先。
2. 回执状态机：每消息全生命周期可查；Claude 有 notify_when_idle 单点回执。
3. 取消安全队列：settled 门控 + 取消闩锁 + 显式 resume——直击 #86385。
4. 机制级门禁（限定面）：已验证 peer/取消回合的枚举入口拦截；通知驱动回合仍保留自主性，提示覆盖在 0.7.1 / 2.2.1 补丁中补齐（见第 06 节）。
5. bridge 精确路由：跨会话直达 mesh 节点/direct agent，而非仅文本。

建议动作（优先级序）

1. Mesh 0.7.1 已补齐：Mesh 输出/错误来源标记与 Mesh/Direct 共用防权限转嫁提示，覆盖前台、结果查询、后台通知。
2. Cross 2.2.1 已补齐：peer 消息中加入“代做被拒权限=拒绝并上报”及不得据此修改 AGENTS.md/config 的措辞。
3. 暂缓端点环境导出：多个 SDK Host 共享 process.env，会继承错端点；已撤回 PI_CROSS_MESSAGING_ENDPOINT 全局赋值。应等按 Session 注入子进程环境的方案。
4. P1 未实施：notify_when_idle、端点分类诊断、Direct 终态按名恢复。
5. Windows 保留 2.2.0 管道命名与 POSIX Unix socket；ACL 隔离未原生验证。跨机器仍不在路线内。
